2. Indices

Los indices usan prefijos JSON para evitar indexar llaves no relacionadas. Solo se indexan rutas usadas en las demos. 

FT.CREATE idx:kb_json ON JSON PREFIX 1 kbj: LANGUAGE spanish SCHEMA $.title AS title TEXT WEIGHT 5.0 $.body AS body TEXT WEIGHT 1.0 $.product AS product TAG SORTABLE $.segment AS segment TAG SORTABLE $.channel AS channel TAG SORTABLE $.updated AS updated NUMERIC SORTABLE

FT.CREATE idx:product_json ON JSON PREFIX 1 productj: LANGUAGE spanish SCHEMA $.name AS name TEXT WEIGHT 4.0 $.description AS description TEXT WEIGHT 1.0 $.type AS type TAG SORTABLE $.segment AS segment TAG SORTABLE $.currency AS currency TAG SORTABLE $.risk AS risk TAG SORTABLE $.channel AS channel TAG SORTABLE $.price AS price NUMERIC SORTABLE $.rate AS rate NUMERIC SORTABLE $.balance_min AS balance_min NUMERIC SORTABLE $.categories[*] AS categories TAG SORTABLE

FT.CREATE idx:place_json ON JSON PREFIX 1 placej: LANGUAGE spanish SCHEMA $.name AS name TEXT WEIGHT 3.0 $.kind AS kind TAG SORTABLE $.city AS city TAG SORTABLE $.services[*] AS services TAG $.location AS location GEO $.hours AS hours TAG SORTABLE

idx:kb_json

Datos: documentos `kbj:*` de ayuda, politicas y seguridad bancaria.

Campos: `$.title` y `$.body` son TEXT para busqueda full-text; `title` tiene mas peso para mejorar ranking.

Filtros: `$.product`, `$.segment` y `$.channel` son TAG porque se usan para coincidencia exacta y facetas.

idx:product_json

Datos: productos financieros `productj:*` como cuentas, tarjetas, creditos, seguros e inversiones.

Campos: `$.name` y `$.description` son TEXT para busqueda por relevancia; `name` pesa mas.

Filtros: `$.type`, `$.segment`, `$.currency`, `$.risk`, `$.channel` y `$.categories[*]` son TAG; `$.price`, `$.rate` y `$.balance_min` son NUMERIC para rangos y ordenamiento.

idx:place_json

Datos: sucursales y ATMs `placej:*` con ciudad, servicios y coordenadas.

Campos: `$.name` es TEXT para buscar por nombre; `$.kind`, `$.city`, `$.services[*]` y `$.hours` son TAG para filtros exactos.

Geo: `$.location` es GEO y permite consultas por radio con longitud, latitud, distancia y unidad.

3. Queries por patron

Ranking de documentos

FT.SEARCH idx:kb_json "tarjeta fraude" WITHSCORES RETURN 4 title product segment channel DIALECT 2
FT.SEARCH idx:product_json "credito personal" WITHSCORES RETURN 5 name type segment rate price DIALECT 2

Datos: documentos `kbj:*` y productos `productj:*` con campos TEXT ponderados.

Sintaxis: `WITHSCORES` muestra el score de relevancia; `RETURN` limita los campos devueltos.

Que demuestra: Redis rankea resultados por coincidencia textual y peso de campos, por ejemplo `title` o `name` pesan mas que la descripcion.

Busqueda por prefijo

FT.SEARCH idx:kb_json "@title:transf*" RETURN 3 title product channel DIALECT 2
FT.SEARCH idx:product_json "@name:cuent*" RETURN 4 name type segment price DIALECT 2

Datos: titulos de documentos y nombres de productos.

Sintaxis: `@campo:prefijo*` busca tokens que empiezan con ese prefijo dentro de un campo TEXT.

Que demuestra: busqueda incremental tipo "el usuario empezo a escribir transf..." sin tener que recorrer todas las llaves.

Coincidencia exacta

FT.SEARCH idx:product_json "@type:{tarjeta} @segment:{empresa}" RETURN 5 name type segment price channel DIALECT 2
FT.SEARCH idx:kb_json "@product:{seguridad} @channel:{app}" RETURN 4 title product segment channel DIALECT 2

Datos: campos categóricos como `type`, `segment`, `product` y `channel`.

Sintaxis: `@campo:{valor}` filtra campos TAG por valor exacto; dos filtros juntos funcionan como AND.

Que demuestra: filtros exactos para facetas bancarias como segmento, canal, tipo de producto o linea de negocio.

Stemming

FT.SEARCH idx:kb_json "inversiones" LANGUAGE spanish RETURN 3 title body product DIALECT 2
FT.SEARCH idx:kb_json "creditos" LANGUAGE spanish RETURN 3 title body product DIALECT 2

Datos: documentos `kbj:*` indexados con `LANGUAGE spanish`.

Sintaxis: `LANGUAGE spanish` aplica el stemmer del idioma al ejecutar la busqueda.

Que demuestra: una busqueda por plural puede encontrar variantes singulares como inversion o credito.

Correccion ortografica

FT.SPELLCHECK idx:kb_json "hipotekario" DIALECT 2
FT.SPELLCHECK idx:product_json "tarjta" DIALECT 2

Datos: vocabulario generado por los campos TEXT del indice.

Sintaxis: `FT.SPELLCHECK indice "termino"` devuelve sugerencias para terminos mal escritos.

Que demuestra: puedes sugerir correcciones antes de lanzar una busqueda o mostrar "quisiste decir..." en canales digitales.

Autocompletado

FT.SUGGET ac:bank_terms "tar" WITHSCORES
FT.SUGGET ac:bank_terms "cred" WITHSCORES

Datos: diccionario de sugerencias `ac:bank_terms` cargado con `FT.SUGADD`.

Sintaxis: `FT.SUGGET key "prefijo"` recupera frases sugeridas; `WITHSCORES` muestra su peso.

Que demuestra: autocomplete controlado por negocio, separado del indice de documentos.

Multiples campos

FT.SEARCH idx:product_json "@type:{credito} @segment:{premier}" RETURN 5 name type segment rate price DIALECT 2
FT.SEARCH idx:product_json "@risk:{bajo} @channel:{app} @currency:{MXN}" RETURN 5 name type risk channel price DIALECT 2

Datos: productos financieros con etiquetas de tipo, segmento, riesgo, canal y moneda.

Sintaxis: varios filtros `@campo:{valor}` se combinan en una sola consulta.

Que demuestra: busquedas operacionales como "productos de bajo riesgo, en pesos, disponibles en app".

Rango numerico

FT.SEARCH idx:product_json "@type:{credito} @rate:[10 20]" RETURN 4 name type rate price DIALECT 2
FT.SEARCH idx:product_json "@price:[100 600]" SORTBY price ASC RETURN 4 name type price segment DIALECT 2

Datos: productos con campos NUMERIC como `rate`, `price` y `balance_min`.

Sintaxis: `@campo:[min max]` filtra por rango; `SORTBY campo ASC` ordena resultados.

Que demuestra: filtros por tasas, comisiones, saldos minimos o montos elegibles.

Geo-radius

FT.SEARCH idx:place_json "@location:[-99.1677 19.4270 5 km]" RETURN 5 name kind city services location DIALECT 2
FT.SEARCH idx:place_json "@city:{Guadalajara} @location:[-103.3918 20.6761 8 km]" RETURN 5 name kind city services location DIALECT 2

Datos: sucursales y ATMs `placej:*` con coordenadas en campo GEO.

Sintaxis: `@location:[lon lat radio unidad]` busca puntos dentro de un radio.

Que demuestra: encontrar cajeros o sucursales cercanas y combinar cercania con filtros como ciudad o tipo.

Aggregations & faceting

FT.AGGREGATE idx:product_json "*" GROUPBY 1 @type REDUCE COUNT 0 AS amount SORTBY 2 @amount DESC DIALECT 2
FT.AGGREGATE idx:product_json "@segment:{empresa}" GROUPBY 1 @risk REDUCE COUNT 0 AS amount SORTBY 2 @amount DESC DIALECT 2

Datos: productos con `type`, `segment` y `risk`.

Sintaxis: `GROUPBY` agrupa, `REDUCE COUNT` cuenta y `SORTBY` ordena la faceta resultante.

Que demuestra: facetas para contar productos por tipo o por nivel de riesgo dentro de un segmento.

4. Cuando usar Redis vs una base relacional

Usa Redis Search and Query cuando...

  • La experiencia necesita busqueda o filtros con latencia muy baja.
  • Quieres combinar texto, TAGs, rangos numericos y GEO en una sola consulta.
  • El usuario espera autocomplete, tolerancia a errores o ranking.
  • Los datos pueden materializarse desde sistemas core, CRM o canales digitales.

Usa la base relacional cuando...

  • Es la fuente de verdad contable o transaccional.
  • Necesitas integridad referencial fuerte y transacciones complejas.
  • La consulta depende de joins profundos o normalizacion estricta.
  • El caso principal es conciliacion, auditoria historica o reporting regulatorio.
